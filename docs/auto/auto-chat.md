# Auto chat

Status: Ask mode built (#463, #455); Run mode writes the Case draft (#456) and runs it (#457), the Test tab applies, trims, rejects and restores it (#458), the Run card pauses, takes over and resumes the Run (#459), messages sent during a Run queue until it ends (#460), the History tab shows the case's health (#461), and Explore reads the Screen, acts on the device and proposes new Test Cases (#462); the chat runs on any Chat-capable Provider (#480). Terms: [`CONTEXT.md`](../../CONTEXT.md) → _Auto_ (Auto chat, Case draft, Proposed Test Case, History summary, Take over), _Providers_ (Chat-capable Provider) and _Catalog_ (Test Case). Why the agent is built this way: [ADR 0012](../adr/0012-auto-chat-agent-harness.md), partly superseded by [ADR 0014](../adr/0014-auto-chat-on-any-chat-capable-provider.md).

## Goal

A new **Auto** screen in the desktop side menu where you test by talking: write a prompt, and an agent works out the steps, runs them on the device and shows the result, without you writing each step by hand or babysitting an agent step by step. The chat has to stay fast and light on context, and what it produces must replay afterwards as a plain Case Script, with no agent, through the normal Run.

## Plan summary

**Agent.** Any Chat-capable Provider is the chat agent (#480, ADR 0014). The Claude Provider runs on the Claude Agent SDK (CLI login or API key), which compacts long chats itself. Every other Chat-capable Provider runs on one agent loop Yoqa owns, on the AI SDK: a streaming text call that repeats while the model calls Yoqa's tools, up to a cap, with its own saved history and compaction. It plans and talks; the Case executor drives the device whenever a Run executes steps, so the chat sees text summaries of steps and never screenshots. Rejected: the Yoqa agent behind a chat UI (cannot diagnose or plan), the SDK acting Action by Action (screenshots fill its context), one adapter per vendor agent SDK (several vendors have none; Groq, Grok and Custom would be left out), moving Claude onto the AI SDK loop (the Claude CLI login only works through Claude Code). Deferred: chatting on the Codex, OpenCode, Cursor and Antigravity CLI logins (each needs its own headless harness). See ADR 0012 and ADR 0014.

**Isolation.** One agent session (Claude) or history (every other Provider) per chat, hosted in the runner. Its only tools are Yoqa's: for Claude served from an in-process MCP server, for every other Provider passed to the AI SDK call. All Claude Code built-in tools (Bash, Read, Write, Edit, Web) are off, and no user settings, CLAUDE.md or skills are loaded. Its working directory is a per-chat folder under `~/.yoqa/`.

**Modes gate tools.** Each message has a mode:

| Mode | Tools |
|------|-------|
| Ask | Read the catalog and Runs. No device. |
| Run | Ask, plus write the Case draft and start Runs. |
| Explore | Run, plus read the Screen, act on the device, and propose a new Test Case. |

**A chat and its case.** A chat belongs to one App and works on at most one Test Case, named in the header. It may start with none; accepting a case that Explore proposes sets it. Another case means a new chat. Chats are saved per App with their messages, their Provider and model, and their agent's session or history, so they resume; deleted only by the user.

**Case draft, never a direct edit.** The agent writes only a Case draft: changed, added and removed steps, each with instructions and an expected result. A Run of the draft runs those steps, not the saved case. Draft steps keep their saved step's id, so changes are shown exactly; rejected: diffing by position or text (a moved or reworded step would show as removed plus added). Reading the draft (`get_case_draft`) is allowed in every mode, since it changes nothing; writing it needs Run.
- Apply needs a Run of the whole draft that passed from a clean start, and applies the whole current draft: its steps and the Case Script that Run learned, together.
- Removing a step from the draft (✕ in the Test tab) clears that pass; the draft must pass again. There is no per-step ✓.
- A Run of a draft does not touch the saved case's Case Script or last result. A passing agent Run of the saved case still saves the Case Script it learned; a Run of a draft hands it back instead (see What shipped).
- Apply keeps one previous version (steps and Case Script); **Restore previous version** in the Test tab swaps them back. No full history.
- Runs from a chat are normal Runs: listed on the Runs page and labelled with their chat.

**Take over.** Pauses the Run and hands the device to the user. Actions taken by hand are not recorded; the agent sees the resulting screen on its next turn. Because Apply needs a clean passing Run, anything done by hand must be reproduced by the draft before it can be saved.

**Step commands.** Each step's command line (e.g. `tap --x 196 --y 488`) comes from the draft Run's own steps, which already know their instruction. The Case Script and the Case Script file format do not change.

**Live updates.** Each chat streams over SSE: text as it is written, tool calls, Run progress. The Run detail page keeps its 1 s poll.

**Provider and model.** One picker in the composer for the chat's Provider and model: every Provider's models grouped under it, and the Providers that cannot chat in their auth mode shown off with why. A new chat starts on the app's default Provider when it can chat, else the first that can, on that Provider's default model. Another model keeps the agent's own history; another Provider starts afresh from the chat's visible conversation. Runs use the app's default vision Provider from Settings whichever Provider writes the chat, shown on the Run card but not changed there.

**Not signed in.** With no Chat-capable Provider signed in, Auto shows an empty state linking to Settings → Providers. A chat whose own Provider was removed, disabled or signed out answers its next message with why and asks for another; no silent fallback to another Provider.

**History.** A History summary per Test Case, computed in the runner over its last 20 Runs, Runs from chats included (they are normal Runs). Pass rate and failing count count the Runs that ended passed or failed; a stopped Run or one in progress is neither, but shows in the chart and the list. The note is a fixed rule, consistent first: the latest Runs that ended failing at the same step, two or more in a row (stopped Runs between them ignored; the same step means the same number and, where both Runs kept their steps, the same text), else flaky when the last five that ended mix passes and failures and ran exactly the same steps. To know that, each Run now keeps the steps it ran (`run_tests.steps_json`, a draft's own steps for a Run of one); Runs from before cannot say, so they never count towards flaky. Rejected: comparing against the case's `updatedAt` (it moves on any edit, name or tags included, and says nothing about a draft Run's steps).

**Queue.** Messages sent during a Run queue in order as removable pending bubbles, and go to the agent together as one turn when the Run ends. Esc stops the Run and keeps the queue. That turn takes the narrowest of the queued messages' modes (Ask over Run), so no message gets tools its own mode does not allow. Rejected: the last message's mode (an Ask question queued after a Run message would get Run's tools), and one turn per mode (the ticket asks for one turn).

## UI

From the owner's prototype (`AutoB.dc.html`, `AutoBPanels.dc.html`):

- **Side menu:** Auto, between Runs and Inspector, at `/auto`.
- **Header:** chat picker (chat title), **New chat**, platform and device pickers. The device is the one you are connected to; the agent never connects or switches devices. While a Run holds it, the device is view-only.
- **Left, the chat:** your prompts; the agent's replies with linked cards (the case, its last Run); a live Run card with progress, the current step, **Pause** and **Take over**; the composer with Ask / Run / Explore, the Provider-and-model picker and Stop.
- **Right, tabs:**
  - **Device:** the live device through the Inspector's Frame Feed, with the current Action overlaid.
  - **Test:** the Case draft as Changes (unchanged steps collapsed, changed and added steps with before and after) or Full test; **Apply** (enabled once a Run of the whole draft has passed), **Reject all**, **Restore previous version**.
  - **History:** pass rate, average time of passing Runs, duration per Run, a per-step strip per Run, and one note set by a fixed rule (no model call). _Consistent failure_ when the last two or more Runs failed at the same step; _flaky_ when the last five Runs mix passes and failures with no change to the steps between them; no note otherwise.

## Scope

Phase 1 is desktop only, with all three modes. No `yoqa chat` command: external agents already use the CLI and the `yoqa-testing` skill.

## What shipped

The design: this doc, the glossary entries and ADR 0012.

**Runs of a Case draft's steps (#463).** The runner can run a Case draft's steps in place of a Test Case's saved ones: `createDraftRun` in the runs domain takes the case, the draft's steps and an optional Case Script. With a Case Script and a mode that allows it, the Run replays it; otherwise the agent runs the steps, on the browser profile the saved Case Script asks for, and the Case Script it learns asks for that profile too. It is a normal Run (listed, with its steps and screenshots), but it never writes to the catalog: the saved case's Case Script, script-saved time and last result stay as they were, including when the Run errors before its case starts. The caller gets an `outcome` promise that settles when the Run is over, with its status, error and the Case Script a passing agent Run learned. Not exposed over HTTP yet; the Auto chat calls it in-process. A draft with no steps is refused.

**The Auto screen and Ask chat (#455).** In the runner (`domains/auto`):
- **Chats** are saved per App in `auto_chats` and `auto_messages` (each message with its mode, the reply's text, its tool calls and any error), with the SDK session id, so the next message resumes the session. A chat's title is its first message. Deleting a chat deletes its messages and its working folder, and stops a reply being written.
- **Routes**: `GET /auto/status`, `GET /auto/models`, `GET|POST /apps/:appId/auto/chats`, `GET|PATCH|DELETE /auto/chats/:id`, `POST /auto/chats/:id/messages` (202: the prompt is saved, the reply streams) and `GET /auto/chats/:id/events`, the chat's SSE stream (`message`, `text`, `tool_call`, `tool_result`, `chat`). The contract is `packages/runner-client/src/auto.ts`. `GET /auto/chats/:id` carries the reply being written, so a screen opened mid-reply can show it. One reply at a time (409 while one is written); Run and Explore answer 400 until their tickets.
- **The chat agent** sits behind a small port (`ChatAgent`: status, models, one turn). The production adapter runs the Claude Agent SDK (pinned `0.3.317`), signed in through the enabled Claude Provider (API key, or the Claude CLI login; never another Provider). Each turn has no built-in tools (`tools: []`), no setting sources, a strict MCP config with only the in-process `yoqa` server, `permissionMode: "dontAsk"` with only the mode's tools allowed, Yoqa's own system prompt, the chat's model, and the chat's working folder under `~/.yoqa/auto-chats/<chat>/` (`YOQA_AUTO_CHATS_DIR` moves it). Streamed text becomes `text` events, and a new text block starts a new paragraph.
- **The Claude Code binary.** Run from source or npm, the SDK starts the Claude Code binary it ships (`@anthropic-ai/claude-agent-sdk-<platform>`). The desktop app's runner is a `bun build --compile` binary, where the SDK cannot resolve that package from inside `$bunfs` and every turn failed with "Native CLI binary for darwin-arm64 not found". There the adapter passes the Provider's own Claude CLI as `pathToClaudeCodeExecutable` (its binary path, else `claude` on PATH or a usual install folder), so in the app an API key also needs the Claude CLI installed; with none the turn says so. Rejected: embedding the SDK's binary in the sidecar (its documented `extractFromBunfs` route) or shipping it beside the sidecar, which grows the app by about 300MB.
- **Ask tools**, answering in text: `get_test_case` (steps, Case Script, last result), `list_runs` and `get_run` (each case's steps, with what each did and why it failed), and `set_test_case`, which sets the chat's Test Case once, while it has none. A tool the mode does not allow is refused by the runner, whatever the agent asks.
- A chat's Test Case comes from **Chat about this case** (`POST …/chats` with `caseId`), or from `set_test_case`. Setting it is one conditional write, so of two attempts at once only one wins.
- The next message waits until the reply before it is saved, so prompts and replies never interleave. Deleting a chat ends its open SSE streams.

In the desktop (`features/auto`):
- **Auto** in the side menu, at `/auto?chat=<id>`, on the selected App. With the Claude Provider signed out it shows an empty state linking to Settings → Providers → Claude.
- **Header:** the chat picker and **New chat**, with the chat's Test Case. The platform and device pickers are the app's top bar, which every screen already shows; Auto adds none of its own.
- **Chat:** the messages, the reply streaming with its tool calls, and the composer with the mode (Explore shown but off until its ticket) and the model picker.
- **Right:** the Device tab shows the connected device's live frames through the Inspector's Frame Feed, view only. History is a placeholder until its ticket.
- **Chat about this case** on a Test Case opens a new chat on it, and selects the case's App.
- The SSE stream has no replay: each time it (re)connects, the screen fetches the chat again, which carries the saved messages and the reply being written. A stream the browser gives up on is opened again while the chat still loads.

**The Case draft (#456).** Run mode answers now, with the Ask tools plus the Case draft's:
- **Draft tools:** `set_draft_steps` (the whole draft at once; a step may name the saved step it rewrites with `savedStep`, and give its own reason), `add_draft_step`, `change_draft_step` and `remove_draft_step`, each with a short reason, and each answering the whole draft as numbered text. `get_case_draft` reads it in any mode. They need the chat's Test Case; Ask refuses the write tools.
- **The draft** (`CaseDraft` in the client contract) is saved per chat in `auto_case_drafts`, gone with the chat or its Test Case. It holds the case's steps when the draft started (`base`), the whole draft in order (`steps`, each with the reason it was changed or added, null while it is as saved) and the saved steps it leaves out (`removed`, with their reasons). A draft step keeps the id of the saved step it came from (added steps get catalog-style `cf_` ids), so before and after are exact. A step as saved is unchanged while it keeps its saved order; one taken out of it (outside the longest stretch of steps still in saved order) is moved, with a reason. A step changed back to its saved text, or a removed step added back as saved, is that step again. A changed step drops its link to a reusable Flow. The catalog is never written.
- Each edit is pushed as a `draft` event, and `GET /auto/chats/:id` carries the draft, so a resumed chat shows it.
- **Test tab:** **Changes** shows changed, moved, added and removed steps (a removed step where it was in the saved case), each with before and after and its reason, and collapses stretches of unchanged steps ("Steps 1–2 unchanged"). **Full test** shows the whole draft in order.

**Running the Case draft (#457).** Run mode adds `run_case_draft` (Ask refuses it):
- It runs the whole draft, from the App's start, on the device the top bar is connected to (its viewport on web), as a Run of the draft's steps (#463): the agent drives it, or the draft's own Case Script replays (executionMode `auto`). It refuses with no device, a device another Run holds, or no draft yet. The tool waits for the Run to end and answers the Run as text (`describeRun`: each step with what it did and its command line, never a screenshot), plus whether it is now the draft's passing Run.
- **Passing Run.** The draft gains `passingRunId` and `learnedScript`. A passed Run of a draft unchanged since it started (same `updatedAt`) sets both: the Case Script the Run learned, or the draft's own it replayed. Every change to the draft clears both, so the draft must pass again. A Run of the draft never writes the saved case (#463). "A clean start" here means the whole draft from the App's start target, never taken over (#459).
- **Which step a Run step is of.** Run steps did not record it, so the Case executor now stamps each agent step's action with `flowStep` (the step of the case, from 0, its instruction came from; the Case Script and its file format are unchanged). The Run card's current step is the last Run step's, or the next once that step's verify accepted the last instruction its step splits into. A replayed Case Script does not say which step each Action is of, so the card lists its commands apart (`replayed`).
- **Run card over SSE.** While the tool waits, the runner reads the Run again every 250 ms and pushes a `run` event (`AutoRun` in the client contract) when it changed, and once more when it ends: status, how it runs, the vision Provider (label and model, the app default; none when replaying), start and end times, the current step and command, and each draft step with its status (pending, running, passed, failed, stopped) and command lines. `GET /auto/chats/:id` carries the Run in progress as `run`. Rejected: hooking progress callbacks into every place the runs domain writes a step or status (several, and easy to miss one); the Run detail page keeps its own 1 s poll.
- **One at a time.** A chat runs one draft Run at a time: a second `run_case_draft` while one is starting or running (the agent may call tools in parallel) is refused. A Run deleted from the Runs page before it ends answers that it was deleted.
- **Stop.** `POST /auto/chats/:id/run/stop` (409 when no Run is in progress) cancels through the Run's own cancel; deleting the chat stops its Run too. The agent's answer says the Run was stopped.
- **Runs page.** A Run stores the chat that started it (`runs.auto_chat_id`, set null when the chat is deleted), and every Run read carries `autoChat` (`{ id, title }`). The Runs page labels such a Run "Auto · <chat title>"; its detail page is the usual one.

**Apply, ✕, Reject all, Restore previous version (#458).**
- **Apply** (`POST /auto/chats/:id/draft/apply`) saves the whole draft to the Test Case: its steps (keeping their ids; a step still linked to a reusable Flow keeps its `flowId`) and the Case Script its passing Run learned, in one transaction with deleting the draft. It answers 409 with the reason, and changes nothing, when the chat has no draft, when the draft has no passing Run, when that Run learned no Case Script (it took no Actions, so the case could not replay), or when the Test Case's steps are no longer the draft's `base`: added, removed, reordered, relinked, or a step's own text edited in Test Cases meanwhile, or restored. Applying would undo that edit, so the user rejects and asks again. Editing a reusable Flow's text is not such an edit: the applied step stays linked to the Flow. Rejected: rebasing the draft onto the edited case (the passing Run was of the old one). The case's last result is left as it was.
- **Recording the pass** is now one transaction too: a passed Run becomes the draft's passing Run only if the draft is still the one that ran, so a ✕ or Reject all that lands as the Run ends is never undone.
- **Previous version.** Apply keeps the steps and Case Script it replaces (`case_previous_versions`, one row per Test Case, the raw Case Script JSON and its saved time). `POST /auto/chats/:id/previous-version/restore` swaps the current and previous versions, so restoring twice returns to the applied one; 409 when there is none. A restored step whose reusable Flow was deleted meanwhile keeps its own text.
- **✕** (`DELETE /auto/chats/:id/draft/steps/:stepId`) removes a step by id, with the reason "Removed in the Test tab", and like any change clears the passing Run and its Case Script. **Reject all** is `DELETE /auto/chats/:id/draft`; the Test Case is untouched. Both 404 when there is no draft (or no such step).
- `GET /auto/chats/:id` carries `previousVersion` (`CasePreviousVersion`: its steps, whether it has a Case Script, when it was replaced), and Apply and Restore push a `previous_version` event; Apply, ✕ and Reject all push a `draft` event (null once applied or rejected). Each route answers the chat.
- **Test tab:** ✕ on each changed, moved and added step in Changes and on every step in Full test; **Apply**, off with the reason under it until the draft has a passing Run (from the `draft` events, so it turns on as the Run passes and off as the draft changes); **Reject all**; and **Restore previous version** whenever the case has one, also once the draft is gone. Apply and Restore refetch the case for Test Cases.

**Pause, Take over, Resume (#459).**
- **Pause** (`POST /auto/chats/:id/run/pause`) stops the Run at the Case executor's pause point, before its next Action, so the Action in flight settles first. The Run stays open (`running`), and the device stays held by it. **Resume** (`…/run/resume`) carries on: the agent takes the Action it had decided on, and a replayed Case Script its next step. Run control lives in the runs domain (`pauseRun`, `takeOverRun`, `resumeRun`), in memory beside the cancel flag; a cancel (Stop, Esc, deleting the chat or the Run) wakes a paused Run so it ends.
- **Take over** (`…/run/take-over`) pauses the same way, then hands the device to the user: the Active Session says `takenOver`, and the runner lets manual Actions through (`POST /action`, `/action/batch` and the control socket's pointer), which it refuses while a Run drives. The Run still holds the session, so it cannot be disconnected or replaced. Resume hands it back.
- **Nothing done by hand is recorded.** It never goes through the Case executor, so it is not a Run step and not in a learned Case Script; the Case draft is untouched. On Resume after a Take over the agent drops the Action it had decided on before (it is also left out of the Case Script), takes a new screenshot of the screen the user left, and decides again. A replayed Case Script carries on with its next step.
- **A Run taken over is not clean.** Even if it passes, it never becomes the draft's passing Run, so Apply stays off; `run_case_draft` tells the agent the user took over and that the draft must pass again without one. Rejected: letting it count (what the user did by hand would not be in the applied Case Script, so the case could not replay).
- **Over SSE.** The Run card's `run` event carries `pause`: `pausing` until the Action in flight settles, then `paused` or `taken_over`; null while the Run goes on. Each control route answers the chat with its Run card read again at once; 409 with the reason when the chat has no Run in progress, or Resume when it is not paused.
- **Desktop.** The Run card shows **Pause** and **Take over** while the Run goes on, **Resume** (and Take over) once it pauses, and a line saying where it is. While taken over, the Device tab drives the device by hand as live control does in the Inspector: a press, drag or tap on the frame is the pointer. The Inspector page stops being view only too, for typing and the rest.

In the desktop: the chat shows the **Run card** under the reply (progress such as "Step 3 of 5", time elapsed, each step with its status and commands, the vision Provider, and **Open Run**); a finished card stays until the next prompt. The composer shows **Stop** while the Run is live, and Esc stops it too, unless it is closing a menu or dialog. The Device tab overlays the Action in flight on the live frame, and says the device is view only while a Run holds it.

**Message queue (#460).**
- **Queued, not sent.** `POST /auto/chats/:id/messages` while the chat's Run is starting or running answers 202 with `{ type: "queued", queued }` (`AutoQueuedMessage`: id, mode, text, time) and starts no turn; otherwise `{ type: "sent", message }` as before. A message sent while messages already wait queues behind them, so the order holds after the Run ends too. The queue is in memory, like the reply being written and the Run's control; deleting the chat drops it.
- **Sent as one turn.** Once the Run has ended (passed, failed or stopped) and the reply it was part of is saved, the queued messages are saved as user messages, in order, and the agent answers them in one turn: one message as usual, several numbered in one prompt, each naming its own mode where it differs from the turn's. The turn's mode is the narrowest of theirs (see Plan summary). A Run that outlives its turn (the agent failed while it ran) sends the queue as it ends.
- **Remove.** `DELETE /auto/chats/:id/queue/:queuedId` takes one back and answers the chat; 404 once it was sent or removed. **Stop** keeps the queue: it only ends the Run sooner.
- **Over SSE.** Each change pushes a `queue` event with the whole queue (empty once it is sent), and `GET /auto/chats/:id` carries `queue`.
- **Desktop.** While the Run is live (or messages wait), Send becomes **Queue** and stays on while the agent's reply is being written, and the hint reads "Enter queues your message until the run finishes · Esc to stop" (after the Run ends, while messages still wait for the agent's reply about it, "Enter queues your message behind the ones waiting"). Queued messages show under the Run card as dashed pending bubbles with their mode and ✕; the bubbles follow the stream's `queue` events only, so a late ✕ answer never brings back a queue already sent. If saving the queued messages fails, those not saved go back to the front of the queue.

**History tab (#461).**
- **History summary.** `GET /cases/:caseId/history` (`CaseHistory`) covers the case's last 20 Runs, newest first: how many passed and failed, the average time of the passing ones, and per Run its number among the case's Runs, the case's status in it, the chat that started it, how long it ran, the step it is on or failed at, and one result per step it ran (passed, failed, skipped, running, pending). Step results come from the agent steps' `flowStep`, the same reading as the Run card's (`runs/step-progress.ts`); a replayed Case Script does not say which step it is on, so a failed replay has no failed step and its steps read skipped, as do an agent Run's that ended before its first step (the App would not start), so neither makes a consistent note. 404 for an unknown case.
- **Steps kept per Run.** Creating a Run writes each case's steps into `run_tests.steps_json` (the draft's, for a Run of a Case draft). The strips use them, so a Run of a 2-step draft shows 2 cells on a 1-step case; a Run from before falls back to the case's current steps.
- **Note.** `consistent` (step, failures, since: the first of them) or `flaky` (passes and failures of the last five), else null, by the rule in Plan summary.
- **Agent.** `get_history` in every mode answers the summary as text: the counts, the note, then a line per Run with its steps.
- **Desktop.** The History tab, from the prototype: the case and **All runs** (the Runs page), the three tiles (Pass rate, Avg pass, Failing), a duration bar per Run (passed, failed, stopped, and a dashed bar for one in progress, capped at the longest that ended) with a tooltip naming the Run, the note, and the Runs with a per-step strip, each opening its Run. The summary is read again each time the chat's Run card moves on (its id, status or step), so the chat's Run shows as it goes. Colors are the Run card's tokens, so both themes follow.

**Explore mode (#462).** Explore answers now, with the Run tools plus three of its own, which Ask and Run refuse:
- **`read_screen`** answers the connected device's cleaned Screen as text (where it was read from, then one row per element: its top left and size on the 0–1000 grid, its id and its label), in the Decide loop's listing (`formatScreenSnapshot`, capped at its row cap). Never a screenshot.
- **`perform_action`** performs one Action through the same `performAction` as `POST /action`: a tap by id, label, x,y or description, input, swipe, drag, key, open-url, an alert or an app's lifecycle. It answers what it did ("Done: tap on "Pay" at 501,500"), and a locator that matches nothing comes back as the answer. It records nothing: no Run, no Case draft. Both device tools are refused with no device connected, and while any Run holds the device (taken over too: that is the user's then).
- **`propose_test_case`** (name, steps, reason) saves a **proposed Test Case** with the chat, in `auto_case_proposals`, pushed as a `proposal` event and carried by `GET /auto/chats/:id` (`proposal`, a `CaseProposal`). Proposing again replaces it. Refused once the chat has a Test Case, checked in the same transaction as the save; and setting the chat's Test Case (`set_test_case`, or Accept) takes the proposal away in the same transaction as it sets the case, so a chat with a case never shows one.
- **Accept** (`POST /auto/chats/:id/proposal/accept`) creates the Test Case on the chat's App with no steps at all (`createCase`'s `withoutSteps`; a case made in Test Cases still gets one blank step), sets it as the chat's case (the same conditional write as `set_test_case`; if the chat got a case meanwhile, the new one is deleted and Accept refused, 409, though setting a case already took the proposal away, so that is only a race), and makes the proposed steps its Case draft, each one Added with the proposal's reason. The proposal is then gone. The steps reach the catalog only through Apply, after a Run of the draft passes, as for any draft. Rejected: creating the case with the proposed steps (nothing left for Apply to prove), and keeping the blank starter step (Changes would show it removed). **Reject** (`DELETE /auto/chats/:id/proposal`) throws it away; nothing was created. Both 404 without a proposal.
- **Desktop.** Explore is on in the composer. Before the chat has a Test Case, the Test tab shows a proposal with its name, reason and steps, **Accept** and **Reject**; after Accept the header names the new case, the picker and Test Cases list it, and the tab shows its draft, all steps Added, with Apply off until a Run of it passes.

**Any Chat-capable Provider (#480).**

Goal: someone with only OpenAI, Google, Groq, Grok, GitHub Copilot, a Custom endpoint, or Codex, OpenCode or Antigravity with an API key can use Auto, and someone with several Providers chooses which one writes each chat. Plan in short: Claude keeps the Claude Agent SDK; one Yoqa-owned AI SDK loop serves every other Provider; a chat capability per auth mode on each driver; a Provider-and-model picker defaulting to the app default. Rejected options are in Plan summary and ADR 0014.

- **Chat capability.** Each driver's `capabilities.chat` lists the auth modes it can chat in, beside `vision`, and the driver catalog carries it to Settings: Claude CLI and API key; Anthropic, OpenAI, Groq, Google, Google Vertex, Grok and Custom API key; GitHub Copilot token; Codex, OpenCode and Antigravity API key only. Cursor none (see Deviations). Every driver the AI SDK loop serves has a chat model factory (`DriverDefinition.chat`) on its vision port's vendor client and key or Base URL resolution, with a cheap credential check (`missingCredential`, no network call). Groq chats on text-only models and without the vision request hooks; GitHub Copilot exchanges its GitHub token and chats on the Copilot API its model listing reads.
- **The AI SDK chat agent** (`domains/auto/ai-sdk-agent.ts`): one turn is `streamText` with Yoqa's system prompt, the mode's Yoqa tools (each through the chat's `callTool`; a tool outside the mode is never offered, and a call to one is refused by the AI SDK before it reaches the runner) and the chat's history, repeating while the model calls tools, at most 25 model calls a turn; past that the reply ends with "The agent stopped after 25 tool steps…". Streamed text becomes `text` events, a new text block a new paragraph. Stop (deleting the chat) aborts it at once, saving nothing. Vendor errors read as the Claude adapter's sentences with the Provider's label: rejected credentials (401, 403), rate limit (429), billing (402, `insufficient_quota`), unknown model (404, `model_not_found`), and a model that cannot call tools.
- **History.** After each turn the agent hands back its history (`agent_history`: the model messages with tool calls and results, its own JSON), saved in `auto_chats.agent_history_json` and passed back next turn, as the Claude SDK session id is. Deleting the chat deletes it.
- **Compaction.** Before a turn, a history over 60% of an 80k-token budget (four characters a token) has its oldest turns, all but the latest 4, replaced by one summary the same Provider and model write in a call with no tools; tool results in those turns are cut to their first 3 lines first. The summary and how many turns it covers are saved at once, so they are not written again, and ride in the system prompt.
- **Prompt cache.** On Anthropic the system prompt and the last history message carry the AI SDK's `cacheControl` breakpoint; other vendors cache by themselves or not at all.
- **Routing** (`domains/auto/routing-agent.ts`): the production `ChatAgent`. It lists every enabled Provider with whether it can chat now and why not (a CLI login only Claude can chat on yet names the key to add, such as "Codex's CLI login cannot run the Auto chat yet; add an OpenAI API key to Codex in Settings → Providers"; a missing key or Base URL; the Claude CLI signed out), and answers each turn on the chat's Provider: the Claude adapter for Claude, the AI SDK agent with the driver's chat model for the rest. A chat with no Provider, or one removed, disabled or signed out, fails its next message with why.
- **Chats.** `auto_chats` gains `provider_id` (not a foreign key, so a removed Provider can be named as removed) and `agent_history_json`. A chat from before keeps the Claude Provider (the default one, else the oldest) and its SDK session, or has none when there was no Claude Provider. A new chat takes the app's default Provider when it can chat, else the first that can, with that Provider's default model (`model` null). `PATCH /auto/chats/:id` takes `providerId` and `model` together: another model of the same Provider keeps the session or history; another Provider drops both, and its first turn carries the chat's visible conversation (`ChatTurn.conversation`: prompts with their mode, reply texts, each tool call on one line), which the adapter puts before the prompt. A Provider that cannot chat, or is not set up, is refused, 400, with the reason. The switch is pushed as a `chat` event. A session or history an agent hands back after the chat switched Provider is dropped.
- **Contract.** `GET /auto/status` is `{ signedIn, detail }`, signed in when any Chat-capable Provider is. `GET /auto/models` is `{ providers, defaultProviderId }`, each Provider with id, kind, label, `available`, `reason`, its models and default model. Chat summaries carry `providerId`. `ChatAgent` gains `providers()` (see Deviations).
- **Desktop.** The composer's picker is a Provider-and-model picker: each Provider under its label and logo (`ProviderLogo`, split out of Settings' `DriverGlyph`), Default first, and a Provider that cannot chat shown off with its reason. The trigger names who answers (`Claude · Opus`). A chat whose Provider cannot answer says so above the composer and asks for another. The empty state says no Provider can chat yet and links to Settings → Providers. The Run card still names the Run's vision Provider.
- **Unchanged.** The tools and their modes, the vendor-neutral system prompt, Case draft, Apply, Take over, the queue (one turn on any Provider), the History summary, and Runs on the app's default vision Provider.

**Deviations from #480.**
- **Cursor cannot chat in any mode.** The spec lists Cursor as Chat-capable with an API key, but a `CURSOR_API_KEY` is only used through the `cursor-agent` CLI; there is no HTTP model API for the AI SDK to call. Cursor's chat capability is empty, and the picker says "Cursor cannot run the Auto chat yet: even with an API key, Cursor runs through the cursor-agent CLI". It joins the CLI-harness follow-up.
- **`ChatAgent.providers()`.** Besides the three port changes the spec names, the port lists the Providers without their models, for a new chat's default and a PATCH's check, since `models()` calls each vendor's model listing.
- **`ChatTurn.agentHistory` and the `agent_history` event.** The spec has the AI SDK history saved per chat; the adapter hands it back as an event, as the Claude adapter does its session id, so the runner saves it and the adapter stays free of the catalog.
- **"Signed in through the `claude` Provider"** was already gone from the glossary's Auto chat entry; the entry now says the chat has a Provider and a model.
- **A model that answers without the tool protocol** (writes a tool call as text) is not detected; only a vendor's refusal of tools is mapped.

## How to verify

The draft Run groundwork: `bun test services/runner/src/domains/runs/draft-run.test.ts` (real catalog in a temp folder, the fake CDP browser, and a fake OpenAI-compatible endpoint as the vision Provider).

The chat: `bun test services/runner/src/interfaces/http/auto.test.ts` (the routes, the SSE stream, the Ask tools, the Case draft tools, Runs of the draft, Apply, ✕, Reject all and Restore, including a script-mode Run of the applied case with Decide set to fail, and Pause, Take over (a tap by hand through the session routes) and Resume, the message queue (order, ✕, one turn, Stop keeping it), the History summary (stats, per-step results, the consistent, flaky and no-note rules on seeded Runs, the chat's Run in progress, and `get_history`), and Explore (its tools and their refusal in Ask and Run, a Screen read and a tap on the fake browser leaving the draft and the Runs alone, proposing, a proposal after exploring holding only the written steps, Accept then Run and Apply, `set_test_case` taking the proposal away, the device tools refused while a Run holds the device, Reject), with a scripted chat agent; the Runs use the real Run engine, the fake CDP browser and a fake vision Provider, `domains/runs/fake-vision.ts`) and `bun test services/runner/src/domains/auto/claude-agent.test.ts` (the contract with the Claude Agent SDK, its `query` faked), and `claude-agent-compiled.test.ts` (a turn from a compiled runner starts the Provider's Claude CLI, a stub here). Any Chat-capable Provider (#480): the same route tests run the real routing agent over catalog Providers with only the turns, the Claude CLI probe and the model listing scripted (status with none, one and several Providers; the models grouped, a CLI login marked unavailable with why; a new chat's default Provider; switching model and Provider and the turn each gives the agent; a Provider that cannot chat refused; a removed or disabled Provider's error; migrated chats keeping the Claude Provider), and `bun test services/runner/src/domains/auto/ai-sdk-agent.test.ts` drives the AI SDK chat agent with the AI SDK's mock language model (streaming and paragraphs, tools through `callTool` and one outside the mode refused, the step cap, Stop, each vendor error, history saved and resumed, the conversation after a switch, compaction, Anthropic cache markers). The chat model factories: `bun test services/runner/src/domains/providers/drivers/chat-models.test.ts`. The replayed Case Script's pause point: `bun test services/runner/src/domains/runs/case-executor.test.ts`. The screen's pure helpers: `bun test apps/desktop/src/mainview/features/auto`.

By hand:
1. Sign in a Provider that can chat (Claude, or any Provider with an API key), connect a device, open **Auto**. With none signed in, Auto shows the empty state with a link to Settings → Providers.
2. On #8, choose **Chat about this case**, and in Ask mode ask "Why did the last run fail?" The reply streams in, read from #8's Runs (the tool calls show in the reply), and the device is untouched.

3. Switch to Run mode and ask "Fix #8: the Sign in button is now Log in." The Test tab fills with the Case draft as you watch: the changed step with its before and after and its reason, the unchanged steps collapsed. Full test shows the whole draft. Open #8 in Test Cases: its steps are as they were. Reopen the chat: the draft is still there.

4. Run mode: "Fix #8 so it passes." The Run card shows each step as it runs, with its commands, the time and the vision Provider, and the Device tab overlays the Action in flight. The Run appears on the Runs page labelled "Auto · <chat>"; #8's saved Case Script and last result are unchanged. Start another and press Esc: it stops.

5. Remove one draft step with ✕: Apply turns off, with why, until the draft passes again. Apply, then replay #8 with `yoqa script run` (or a script-mode Run): it passes with no Provider call. The Test tab shows no draft, and #8 in Test Cases has the new steps.
6. **Restore previous version** brings back the old steps and Case Script; pressing it again brings back the applied ones. **Reject all** on a new draft leaves #8 as it is.
7. Run the draft and press **Pause** on the Run card: it stops after the Action in flight, says Paused, and **Resume** carries on. Press **Take over**: the Device tab says you have the device, and a tap or drag on the frame drives it. **Resume**: the agent looks at the screen you left and goes on. The Run may pass, but Apply stays off until a Run of the draft passes without a Take over, and the Run's steps and the draft hold nothing you did by hand.
8. Run the draft and, while it runs, send two messages: they show as queued bubbles under the Run card, and ✕ takes one back. Press Esc: the Run stops, the queue stays, and once the agent's reply about the Run is in, the queued messages appear as sent and the agent answers them together.
9. Open the **History** tab on a case with a few Runs: the pass rate, the average passing time and the failing count, a bar per Run and a strip per Run. Run the draft: its Run shows dashed in the chart and running in its strip, then lands as passed or failed. Fail the case twice at the same step (a step the app cannot do): the note says "Consistent failure, not flaky." In dark mode the same.
10. Start a **New chat** with no Test Case, pick **Explore** and ask "Find something on the checkout worth testing." The agent reads the Screen and taps through it (the Device tab shows it), then proposes a Test Case: the Test tab shows it with Accept and Reject. Accept: the header names the new case, Test Cases lists it with no steps yet, and the Test tab shows its draft, every step Added. Ask it to run the draft; once it passes, Apply saves the steps and the Case Script. In a chat on #8, ask Explore to propose a case: it says the chat already has one.
11. With an OpenAI (or Groq, Google, Custom…) Provider and the Claude Provider both set up, open the composer's picker: each Provider lists its models under its label and logo; a Codex, OpenCode or Antigravity Provider on its CLI login is shown off, saying which API key would make it work. Start a **New chat**: it is on the app's default Provider. Ask about #8 on OpenAI: the reply streams with its tool calls. Switch to Claude and ask "What did you just tell me?": it answers from the conversation so far. Delete the OpenAI Provider in Settings and send again on a chat that used it: the reply says its Provider was removed, and the composer asks for another.

## Follow-ups

- The chat Run follows a Run by reading it every 250 ms while the tool waits. If the runs domain gains a change feed, the Run card could use it instead.
- A failed Run of an unchanged draft keeps an earlier passing Run. If a flaky pass should not be enough to apply, clear the pass on any failed Run of the whole draft.

- Compare two Runs from the History tab.
- A failed Case Script replay names no failed step, so a case that fails in script mode never gets a consistent note, and a replay in progress shows all its steps pending. If replayed actions recorded their step of the case, both could.
- The History reads its last 20 Runs one by one (`loadRun` each, steps included). Fine at 20; a case with long Runs could read only the steps' results instead.
- The History tab reads the summary again when the chat's own Run moves on, or on focus. A Run started elsewhere (the Runs page, the CLI) shows on the next read; a runs change feed could push it.
- In Chrome an `EventSource` opens only once the first bytes arrive, and the chat's stream sends none until something changes, so a chat opened in Chrome (the e2e webview) stays loading. The desktop's own webview was not checked for the same. Sending an SSE comment as the stream opens would settle it either way.
- Codex as a second harness once the `codex` Provider supports a CLI login.
- Recording Take over Actions into the draft, if reproducing them by hand turns out to be painful.
- The packaged runner: the SDK starts Claude Code from a per-platform optional package, which the bundled npm runner may not carry. Check a packaged build; if it is missing, ship the SDK unbundled or point `pathToClaudeCodeExecutable` at the Claude CLI.
- Deleting a chat leaves its SDK session transcript under `~/.claude/projects/`; delete it with the SDK's `deleteSession` too.
- The Case draft compares against the case's steps as they were when it started (`base`). If the Test Case is edited in Test Cases meanwhile, Changes still shows the old before, and Apply refuses it (#458). The Test tab could say so before the user presses Apply.
- Reject all has no confirm (as Delete chat). If drafts get thrown away by mistake, add one.
- Reject all or Apply while a Run of the draft is going leaves that Run going (it no longer counts for anything). They could stop it.
- Pause and Take over are on the Auto chat's Run card only. The Runs page and the CLI cannot pause a Run; the runs domain can (`pauseRun`), so they could.
- While taken over, the Device tab takes the pointer only (tap, press, drag). Typing and keys go through the Inspector page, which is no longer view only then; the Device tab could take them too.
- A Take over during a replayed Case Script carries on with the script's next step, blind to what the user changed. It could fall back to the agent instead.
- The chat agent hears that the user took over (in `run_case_draft`'s answer), but in Run mode it has no tool to read the Screen, so it never sees the screen they left itself; the Run's agent does, on Resume. In Explore it can read it once the Run ends.
- Resume pressed in the middle of a drag by hand hands the device back before the drag's release reaches it, which is then refused. Resume could wait for the pointer to come up.
- The queue lives in memory: a runner restart during a Run loses it (and the Run). If that bites, keep it in `auto_messages` as pending rows.
- After the Run ends, while the agent still writes its reply about it, a message sent with nothing queued is refused (409, one reply at a time), as before. It could queue too.
- Queued messages of different modes answer in the narrowest one, so a Run-mode message queued beside an Ask question cannot change the draft in that turn; the agent says Run mode will do it.
- The `previous_version` event goes only to the chat that applied or restored. Other chats on the same Test Case see the change when they are opened again.
- The model list for an API-key login reads the Anthropic models endpoint each time; it could use the Provider's cached list (`listProviderModels`).
- Explore's Actions answer only what they did; the agent reads the Screen again to see the result. `perform_action` could settle and answer the new Screen in the same call, as `yoqa action --screenshot` settles before its screenshot.
- `read_screen` uses the Decide loop's row cap (80 rows) and has no `limit` or full tree. If the agent misses elements on long screens, give it a limit.
- An accepted proposal whose draft is rejected (Reject all) leaves the new Test Case with no steps in the catalog. Delete it from Test Cases, or Reject all could offer to.
- A proposal is accepted whole, as a draft is applied whole. Editing a proposal before Accept is the agent's job (propose again).
- Chatting on the Codex, OpenCode, Cursor and Antigravity CLI logins (#480 out of scope): each needs a harness that drives the CLI headless with Yoqa's tools on a runner MCP endpoint. Cursor's API key needs the same, since it too goes through `cursor-agent`.
- The context budget for compaction is one fixed figure (80k tokens, four characters a token). A model with a smaller window (a local model behind Custom) can overflow before it compacts; a per-model or per-Provider budget would fix it.
- A model that writes its tool call as text, instead of the tool protocol, ends its turn as plain text; it could be detected and failed with the "cannot call tools" sentence.
- GitHub Copilot exchanges its GitHub token for a Copilot token on every turn; caching it until it expires would save a request.
- The chat's Provider and model are not shown in the chat picker's list, only in the composer's picker.
